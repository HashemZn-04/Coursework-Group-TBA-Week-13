## 3. Bugs found and fixed

An independent adversarial re-read (fresh context, hand-verified the forecast
and clustering math, re-ran the suite) confirmed all five of these and found
nothing further genuinely broken — its only note was that the three
normalisation fixes below aren't yet covered by a test that seeds mixed-case
category data, so they'd currently pass identically with or without the fix.
Worth adding if anyone has ten minutes; not done this session since it wasn't
asked for.

1. **`streamlit_app.py`** still described "Receipts / Verdicts / Decisions /
   Cluster Reviews tabs" — stale since the schema collapsed to one Receipts
   tab (`handoff_4.md`). Fixed to "Receipts / Cluster Reviews".

2. **`scripts/h1_demo.py`'s `history()` helper defaulted to `verdict="low"`**,
   the pre-2026-09-09 legacy value. The script builds its DataFrame directly
   rather than through `dashboard.data.load_receipts()` (which normalises
   legacy verdicts on read via `api.policy.normalise_verdict`), so every
   "working" scenario in the script silently fell through to
   `TRAVEL_SPEND_UNPROCESSED` instead of producing a forecast. The script's
   own mismatch-detection caught it — it exited 1 — so this had been failing
   silently until someone actually ran it this session. Fixed by changing the
   literal to `"low_risk"`.

3. **Category not normalised before grouping/filtering, in three places** —
   the exact class of bug `dashboard/policy_health.py`'s `breakdown()` already
   guards against (its own comment: "the sheet holds both `Travel` from n8n
   and `travel` from the audit engine"), missed in:
   - `pages/1_Spend_Overview.py`'s "Spend by category" chart —
     `groupby("category")` on the raw column split one category across two
     bars.
   - `pages/3_Expense_Browser.py`'s category multiselect and filter — same
     raw-column comparison, so filtering by "Travel" missed every "travel"
     row.
   - `api/app.py`'s `/api/expenses?category=` — exact string match on the raw
     column; a caller querying `category=travel` missed n8n's `Travel`-cased
     rows.
   All three now go through `api.policy.normalise_category` on both sides of
   the comparison. `api/app.py` already imported it for the audit endpoint;
   no new import needed there.

4. **Real data corruption via `value_input_option="USER_ENTERED"`** —
   `api/sheets.py`'s `insert_receipt()` (the actual `/api/audit` write path)
   wrote `receipt_date` with `USER_ENTERED`, which lets Google Sheets'
   smart date-detection reinterpret an ambiguous `DD/MM/YYYY` string
   (day ≤ 12) using its own locale. **Proved live**: wrote `"05/01/2026"`
   (intended 5 January), read back `"1/5/26"` (1 May) — a genuine four-month
   corruption, silent, no error. This is a live production-code bug, not just
   a mock-data artifact — anyone calling `/api/audit` with a day-first date
   where the day is ≤ 12 is at risk. Fixed by switching to
   `value_input_option="RAW"`, which stores the literal text; verified numeric
   columns (`total_amount` etc.) still come back correctly typed as numbers
   under `RAW`, not strings. `scripts/seed_mock_data.py`'s own writes use the
   same fix (see §5 — this is *why* the mock data had to be rewritten once).

## 5. Mock data — three attempts, here's what landed

**First attempt** (135 rows, GBP only, Nov 2025–Aug 2026): travel/
accommodation/subsistence/client_entertainment with independent RNGs per
category, tuned by seed search against the actual `forecast_next_month()`
output until it produced a believable R²≈0.61 fit. Written via
`api.sheets.insert_receipt()` — then discovered that function hardcodes
`created_at`/`decided_at` to *now*, ignoring whatever's passed in, so every
backdated mock row would've looked submitted today. Switched to writing
directly via `receipts_ws().append_rows()` instead, with `created_at`/
`decided_at` computed relative to each row's own date.

**Discovery of the real blocker**: reading the sheet back through
`dashboard.data.load_expenses()`, the forecast refused with
`MIXED_CURRENCY_HISTORY`. Root cause: the live Travel category already held
21 pre-existing EUR/USD rows, 20 of which turned out to be exactly the lazy
Gemini pattern the user described — `Hilton`/`Uber`/`Starbucks`,
receipt_id 14–113 (100 rows, verified contiguous), scaling in perfect
lockstep from 10 to 1000, currency cycling GBP→USD→EUR every ~40 rows, no
line items, dates that don't form a real timeline. User confirmed deleting
exactly those 100 rows (and only those — a single remaining USD row,
receipt_id 1, "Delta Airlines" $450, was confirmed as a real standard US
receipt to keep, not touched).

**Redesign**: user then asked for a near-even three-way currency split — 200
each of GBP/USD/EUR — spanning random days Sept 2025–Aug 2026, with the Delta
Airlines row staying as-is. Since `forecast_next_month()` correctly refuses on
a mixed-currency history (deliberate, documented — "nothing converts between
currencies"), a genuinely multi-currency Travel category needs the forecast
filtered to one currency before fitting, which the page didn't do. Added a
currency picker to the forecast section on `pages/1_Spend_Overview.py`
(mirrors the selectors the other charts already have) and made
`dashboard/forecast_view.py`'s `render_forecast()` actually filter `expenses`
by the selected currency (via `dashboard.spend.currency_key`) before calling
`forecast_next_month()` — previously the `currency` parameter it received was
only ever used as a display-label fallback, never for filtering.

Rebuilt `scripts/seed_mock_data.py` around one `PROFILES` dict keyed by
currency — GBP (Trainline/LNER/EasyJet/British Airways/Uber/Premier Inn/...),
USD (Delta/American/United/Amtrak/Hertz/Marriott/Uber/Lyft/...), EUR (Deutsche
Bahn/SNCF/Eurostar/Lufthansa/Air France/NH Hotels/...), each with its own
trip-count trend and independent RNG seed, so tuning one currency never
shifts another's numbers. Seed-searched each currency independently against
`forecast_next_month()` until R² landed in a believable 0.5–0.85 band (not
suspiciously perfect, not noise) — locked at GBP seed 102, USD seed 18, EUR
seed 26 (all in `DEFAULT_SEEDS` in the script).

**Then the date bug (§3.4) surfaced** while investigating why the *combined*
forecast was noisier than the clean per-currency simulation predicted: some
of the freshly-written rows had `receipt_date` values that had round-tripped
through Sheets with day and month swapped, spilling into Sept–Dec 2026 and
pushing the forecast's anchor month to January 2027. Deleted both mock
batches (receipt_id 134–836, confirmed contiguous), fixed the write to use
`RAW`, and rewrote once more.

**Final state, verified against the live sheet** (not a local simulation):

| Currency | Travel rows | Sept 2026 forecast | R² | RMSE |
|---|---|---|---|---|
| GBP | 84 | £1,689 (range £1,301–£2,078) | 0.80 | £181 |
| USD | 80 (incl. the original Delta Airlines row) | $2,282 (range $1,358–$2,906) | 0.70 | $377 |
| EUR | 75 | €1,684 (range €1,278–€2,089) | 0.84 | €189 |

568 new rows total (receipt_id 34–601): GBP 211 / USD 196 / EUR 191 across
Travel/Accommodation/Subsistence/Client Entertainment, close to the requested
200-each split. `api/forecast.py`'s `forecast_next_month()` also gained an
`rmse` field on the `model` dict (plain in-sample RMSE, `sqrt(mean(residual²))`
— distinct from the existing `residual_std`, which divides by `n-2` for the
confidence-band math and was already there); `dashboard/forecast_view.py`
renders it as its own metric tile next to R².

`scripts/seed_mock_data.py --dry-run` previews without touching the sheet;
omit the flag to regenerate (it appends, doesn't replace — delete old
receipt_id ranges by hand first if regenerating from scratch, the same way
this session did).
